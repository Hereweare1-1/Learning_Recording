# 存储引擎选择

选择存储引擎时，需要结合事务、数据可靠性、并发量、读写模式和数据是否允许丢失等要求进行判断。

> [!tip] 当前阶段的默认选择
> 普通业务表优先使用InnoDB。只有在需求非常明确，并且能够接受其他引擎的限制时，才考虑MyISAM或MEMORY。

## 1. 选择InnoDB

出现以下任意需求时，优先选择InnoDB：

- 需要事务、提交和回滚。
- 需要外键保证引用完整性。
- 数据不能因为服务器异常而丢失。
- 存在较多的更新和删除操作。
- 需要多个用户高并发读写。
- 需要较强的崩溃恢复能力。

InnoDB支持事务、行级锁、外键和崩溃恢复，是MySQL 8.4的默认存储引擎，适合大多数Web业务系统。

## 2. 选择MyISAM

只有同时满足以下大部分条件时，才考虑MyISAM：

- 数据主要用于只读或读多写少的场景。
- 写入并发量较低。
- 不需要事务和回滚。
- 不需要外键。
- 数据能够通过其他方式恢复，或者属于已有的遗留系统。

MyISAM使用表级锁。即使单次读取或批量插入在某些场景中较快，高并发写入时也容易因为锁住整张表而产生等待。因此，不能只因为“查询多”或“插入多”就直接选择MyISAM。

## 3. 选择MEMORY

只有同时满足以下条件时，才考虑MEMORY：

- 数据量较小，能够完全放入内存。
- 数据是临时的或可以重新生成。
- MySQL重启后数据丢失不会影响业务。
- 以读取为主，并发写入较少。
- 已经通过真实业务测试确认它比InnoDB更合适。

MEMORY适合临时工作区或非关键缓存，不适合保存订单、账户、用户资料等重要数据。

虽然数据保存在内存中，但MEMORY使用表级锁，因此在高并发读写场景中不一定比InnoDB快。

## 4. 快速决策流程

```text
是否需要事务、外键、数据持久性或高并发写入？
├─ 是 → 选择InnoDB
└─ 否
   ↓
数据是否允许在MySQL重启后丢失，并且能够完全放入内存？
├─ 是 → 可以评估MEMORY，并进行实际测试
└─ 否
   ↓
是否属于只读、读多写少、低并发或需要兼容的遗留场景？
├─ 是 → 可以评估MyISAM
└─ 否 → 选择InnoDB
```

## 5. 选择对照表

| 业务需求 | 推荐引擎 | 原因 |
| --- | --- | --- |
| 订单、支付、库存、用户数据 | InnoDB | 需要事务、可靠性和并发控制 |
| 普通Web应用业务表 | InnoDB | 功能完整，适合持续读写 |
| 只读或读多写少的遗留表 | MyISAM | 可以兼容原有设计，但应先评估迁移到InnoDB |
| 可以重新生成的小型临时数据 | MEMORY | 内存访问，重启后数据可以丢失 |
| 重要缓存数据 | InnoDB或专用缓存系统 | MEMORY不提供持久性，不应仅因名称中有“内存”就直接使用 |

## 6. 混用存储引擎的风险

MySQL允许同一个数据库中的不同表使用不同的存储引擎，但不应在没有明确理由的情况下混用。

如果一个事务同时修改InnoDB表和MyISAM表，执行`ROLLBACK`时只能回滚支持事务的InnoDB表，MyISAM表中的修改不会被撤销，这会破坏业务操作的原子性。

混用还会增加备份、恢复、监控和问题排查的复杂度。对于普通项目，统一使用InnoDB通常更简单可靠。

## 7. 查看和转换存储引擎

查看表当前使用的存储引擎：

```sql
SHOW TABLE STATUS LIKE 'employee';
```

把现有表转换为InnoDB：

```sql
ALTER TABLE employee ENGINE = InnoDB;
```

转换之前需要检查表结构、外键、索引、数据量和停机影响，并在测试环境中验证。
